# 升级指南（1.0.0 → 1.1.x 及以后）

> 目标：升级扩展版本时**不丢分组、站点、文件夹、组件配置、AI 设置**。
> 结论先给：**保持扩展所在目录不变，用新版本文件覆盖旧文件，再点「重新加载」即可，数据自动保留。**

---

## 1. 数据存在哪里

| 数据 | 存储位置 | key |
| --- | --- | --- |
| 分组 / 站点 / 文件夹 / 组件 / 偏好设置 | `chrome.storage.local` | `qihang-nav-v1` |
| AI 组件（模型、接口地址、提示词、会话） | `chrome.storage.local` | `qihang-ai-v1` |
| 远程同步配置（QSP 地址、令牌、rev） | `chrome.storage.local` | `qihang-sync-v1` |

关键点：

- `chrome.storage.local` **按扩展 ID 隔离**，不按版本隔离。只要扩展 ID 不变，升级版本不会碰数据。
- 未打包（加载已解压）的扩展，其 ID 由**加载目录的绝对路径**派生。因此「换目录 = 换 ID = 读不到旧数据」。
- key 名里的 `v1` 是**存储结构版本**，与扩展版本号（1.0.0 / 1.1.x）无关，跨版本固定不变。

## 2. 版本升级时数据怎么迁移

页面启动时读取 `qihang-nav-v1`，交给 `normalizeData()` 清洗（`src/js/store.js`）：

- 缺失字段补默认值（例如 1.0.0 没有 `settings` 里的新项时自动补上 `DEFAULT_SETTINGS`）
- 丢弃非法条目（无 URL、无名称的分组）
- 嵌套文件夹降级为只保留一层
- `activeGroupId` 指向的分组不存在时回落到第一个分组
- 清洗结果为空则使用默认数据

所以**同一 key 内的旧结构会在读取时自动对齐新结构**，不需要手写迁移脚本。只有将来出现无法兼容的结构变更时，才需要换 key（如 `qihang-nav-v2`）并在 `main.js` 启动流程里做一次性搬运。

## 3. 标准升级流程（推荐，约 1 分钟）

前置：先备份，双保险。

1. **导出备份**：打开新标签页 → 右上角设置 → 备份与恢复 → **导出备份**，得到 `qihang-nav-YYYY-MM-DD.json`
2. **替换文件**：把新版本 zip 解压，覆盖到**原来那个目录**（保持路径完全一致，例如 `D:\Extensions\qihang-nav`）
   - 直接覆盖即可，不必删除旧目录；`manifest.json`、`src/`、`doc/` 等整体替换
3. **重新加载**：打开 `chrome://extensions` → 找到「启航 · 新标签页导航」→ 点「重新加载」（🔄）
4. **刷新新标签页**，确认分组、站点、文件夹、组件都在

> 不要点「移除」再重新「加载已解压的扩展程序」——移除会连带清掉该扩展的存储数据。

## 4. 1.0.0 → 1.1.x 具体差异（本次升级要验证的点）

1.1.0 相对 1.0.0 新增了文件夹、书签同步、AI 组件相关字段；1.1.1 新增设置区块折叠与定时备份。旧数据里没有这些字段，`normalizeData` 会补默认值，**不需要额外操作**。

升级后按此清单核对：

- [ ] 原有分组名、站点顺序、图标都在
- [ ] 每行图标数、对齐方式、背景等偏好保持原样
- [ ] 右键 →「添加组件」能看到时钟与 AI
- [ ] 把一个图标拖到另一个图标中间，能生成文件夹
- [ ] 设置 → 备份与恢复能正常导出 JSON
- [ ] 若配置了远程同步，点「从服务器恢复」不报错

## 5. 换目录 / 换电脑 / 重装

这些场景扩展 ID 会变化，旧数据读不到，必须走备份：

1. 旧环境：设置 → 备份与恢复 → **导出备份**（JSON）
2. 新环境：安装扩展 → 设置 → 备份与恢复 → **导入备份** → 选择 JSON
3. 导入后 `state = normalizeData(parsed)` 会做同样的结构对齐

若旧环境已无法打开，也可以用远程同步（QSP）：新环境填同样的服务端地址与令牌，执行「从服务器恢复」。

## 6. 回滚到旧版本

数据只增不减，旧代码读到新数据时：

- 未知字段会被忽略（不报错），已存在的分组与站点正常显示
- 若新版本新增过文件夹，旧版本会把文件夹里的站点按非文件夹条目处理或丢弃，**建议回滚前先导出备份**

回滚步骤：把旧版本文件覆盖回同一目录 → 重新加载 → 刷新页面。

## 7. 会丢数据的操作（务必避开）

| 操作 | 后果 | 规避 |
| --- | --- | --- |
| 扩展页点「移除」后再加载 | 该扩展存储被清除 | 用「重新加载」而不是「移除」 |
| 换一个目录加载新版本 | 新扩展 ID，读不到旧数据 | 覆盖原目录，或先导出备份再导入 |
| 清理浏览器「Cookie 及其他网站数据」并勾选扩展数据 | 存储被清除 | 定期导出备份 |
| 用无痕窗口 / 临时用户配置 | 独立存储，关窗即丢 | 在正常窗口使用 |
| 直接编辑 `chrome.storage` 或手工改备份 JSON | 结构非法会被清洗丢弃 | 改前先备份 |

## 8. 发布侧：版本号一致性

一次版本升级要同步这些位置（GitHub Actions 也会校验 tag 与 `manifest.json` 是否一致，不一致直接失败）：

| 位置 | 内容 |
| --- | --- |
| `manifest.json` | `"version": "1.1.1"`（唯一权威） |
| `src/newtab.html` | 页脚 `启航 · v1.1.1` |
| `README.md` | 下载链接、文件名、Release 说明中的版本 |
| `doc/BACKUP-MANIFEST.md` | 压缩包名、包内文件数、包大小 |

发布动作：

```powershell
git tag -a v1.1.1 -m "qihang-nav v1.1.1"
git push origin v1.1.1
```

推送标签后由 `.github/workflows/release.yml` 自动打包并发布到 Release 页面，无需手工上传。
